# AtomEngine editor and renderer direction

## Target shape

Keep the native Direct3D 12 backend. Replace global, sample-owned control flow in measured steps instead of rewriting the backend before there is a working editor.

```text
Editor application
  ├─ Editor document, selection, undo/redo, panels, commands
  ├─ Scene: stable entities + Transform, Camera, Light, and Model components
  ├─ Asset database: source paths/IDs, import settings, CPU asset data
  └─ Engine runtime
       ├─ Renderer: view extraction and frame submission
       ├─ Render graph: pass/resource dependencies and barriers
       └─ D3D12 backend: device, queues, frame contexts, descriptors, resources
```

## Decisions

- **Direct3D 12 remains the backend.** It already supports the project's bindless materials, compute shaders, temporal post processing, and Windows target. A second backend would dilute effort without helping editor workflows.
- **The editor is a separate application target.** `PBR` remains a useful sample. Both targets reuse the same engine and scene renderer; editor panels do not live inside the renderer implementation over time.
- **Scenes describe instances; assets describe reusable content.** A scene object holds an asset reference and a transform. GPU buffers and textures belong to shared assets, not to each object. Runtime scene objects now receive stable 64-bit IDs, selection resolves through those IDs, and scene format version 3 persists models, cameras, directional lights and active references (the loader also migrates versions 1 and 2). Editor edits, imports, and deletions use an explicit command boundary with undo/redo; opening a different document clears the previous history.
- **A render graph is the destination for frame orchestration.** Passes declare reads, writes, queue requirements, and outputs. The graph owns resource lifetime and transitions; individual passes own PSOs and draw/dispatch logic. Existing passes migrate one at a time.
- **Frame resources are fence-owned.** Upload memory, transient descriptors, and per-frame command allocators are retired only after their frame fence completes. GPU uploads move off the synchronous model-loading path once the asset workflow exists.
- **The editor viewport is an explicit render view.** Its camera, pixel size, render target, and temporal history are independent from the main window and other future views.

## Migration stages

1. Add a standalone editor target and usable scene hierarchy, inspector, content browser, and scene files while sharing the stable PBR renderer.
2. Move editor UI orchestration and document commands fully out of `PbrRenderer`; add an undoable command boundary. Implemented: `EditorMain` creates `EditorLayer`, which owns panels, selection, scene dialogs, and command history. `PbrMain` creates a sample UI with no editor dependency. Both use `PbrApplication` for ImGui and application lifecycle. `PbrRenderer` and `PbrResources` now live in `Atom/src/Renderer` and compile once into Atom core. Applications do not compile sample renderer source. `PbrRenderer` takes a scene, view and shared resources and records rendering into a caller-owned command context; it has no ImGui dependency or entry point.
3. Introduce an explicit engine/application lifetime and a per-viewport render-view API. Implemented: the application owns the scene, `RenderView`, renderer, camera controller, UI, and shutdown order. Each view owns its render camera, independent editor navigation camera, scene-camera preview mode/source, pixel dimensions, color/depth/normal targets, shadow target, SSAO intermediates, and TAA history/state. UI returns a `ViewportRequest` in pixels; the application applies it before rendering. Presentation resize no longer recreates PBR view resources. GPU work finishes before target recreation and cleanup. Input capture, the device/backend caches and SSAO pipelines/random texture still use process-wide state; shared PBR IBL resources have an explicit application owner.
4. Add a small render graph for the current forward PBR path: depth/normal, shadow, AO, opaque+sky, temporal/post, editor composition. Compare output against the current path after each pass moves. The graphs now own depth/normal, shadow depth and publication, SSAO dependencies, opaque+sky rendering, and temporal resolve/history publication. The application records display composition and editor UI outside the render graph.
5. Separate CPU assets from GPU residency and make import/upload asynchronous with cancellation and diagnostics. Implemented: CPU-only glTF decoding produces meshes, decoded RGBA images, and material image indices. `ModelAssetManager` owns a CPU worker and canonical-path cache. The render thread submits one complete asset upload per update and publishes residency only after its fence. Instances share immutable CPU assets and GPU geometry/materials. The content browser exposes task state/cancellation, model-cache budgets and residency, and records a scene command only when an asset is ready. Request leases and external scene/history/frame owners protect ready entries; unused CPU/GPU residency is evicted in LRU order and model textures recycle both SRV descriptor slots. `SceneDocumentLoader` parses documents on its own worker, requests shared assets incrementally, and commits the complete scene on the render thread.
6. Add broader renderer features (deferred/clustered lighting, multithreaded recording, richer post) only on top of the graph and frame-resource ownership.

## First editor milestone

The editor starts from the current working PBR scene, allows selecting and transforming models, cameras and directional lights, imports `.gltf`/`.glb` assets from the content browser, and saves/loads a portable scene document. It keeps the viewport and post-processing controls available while making scene editing the main workflow.

## Current frame and resource rules

- `PbrApplication` builds UI, records geometry, AO, lighting, and post processing, then draws the main UI on the same direct command list. It submits without a per-frame completion wait. Secondary ImGui windows use the same direct queue and submit afterwards, before the main window presents. Same-queue ordering protects view targets/history across queued frames and detached windows. Compute shaders still run, but this path currently makes no async compute overlap claim.
- ImGui uses its current DX12 initialization API with the engine's direct queue and descriptor allocation/free callbacks. The backend manages dynamic font textures; the application does not call the legacy font-atlas `Build` method. Retired UI descriptor slots are reused within the application session.
- The main backbuffer transitions to render target before UI drawing and to present afterwards. The scene target matches the viewport panel's pixel dimensions; camera aspect and TAA history update when that target changes. Zero-sized requests preserve the previous target. Target dimensions are clamped to 8–16384; odd dimensions use rounded-up half-resolution SSAO targets and clamped edge loads.
- The primary swapchain obtains its current backbuffer index from `IDXGISwapChain3` after creation, resize and Present, including occluded/minimized states. Application frame slots and UI backend buffer rings are bounded independently of this presentation index.
- A directly indexed root signature binds its descriptor heap before setting the signature. The command-context cache restores both after a pass switches to a dynamic heap, even when the signature pointer is unchanged.
- Texture SRVs retain a CPU descriptor mirror for descriptor copies; shader-visible descriptors are destinations. Resource transitions update the owning wrapper, including initial texture uploads and the SSAO random texture.
- IBL specular prefilter constants use a floating-point roughness matching the shader constant buffer.
- Geometry, lighting, post, and SSAO graphs reference view-owned resources. PBR descriptor tables are local to the renderer/view pair. Two immutable post tables reference the two TAA history variants; these and the common table are rewritten only after GPU-idle view resize. The application initializes one `PbrResources` object, owning the graphics/compute pipeline wrappers, eight IBL/BRDF/SSS buffers and cached skybox model. Views share this object without repeating precomputation or rebuilding global PSOs. Pipeline attachment formats are validated; incompatible view formats fail before descriptor allocation. View shutdown clears only that view's graphs, leaving other views' shared resources intact. After draining GPU work, the application shuts down all views and then their shared buffers. Backend PSO/root-signature caches and the SSAO random texture remain device-scoped.
- PBR/Editor disable both legacy display-sized scene buffers and global IBL buffers; they use the explicit view/shared-resource owners. The legacy sample path still creates its own global buffers. The null material SRV now belongs to `TextureManager` and is created once after the bindless heap, so CPU/GPU model import has no dependency on legacy renderer initialization.
- `FrameScheduler` owns three application slots. Begin waits only when reusing an incomplete slot, then releases that slot's retained owners. UI viewport descriptors are indexed by this slot, independently of the swapchain backbuffer index. Each recorded scene frame retains distinct shared `ModelGPU` owners until its slot fence completes. `GameCore::OnFramePresented` lets the application signal its fence after main rendering, texture uploads, detached-window rendering and presentation. The application drains its slots before UI/scene/renderer cleanup; view and swapchain resize still idle the GPU. Command allocators, constant/upload pages and dynamic descriptor heaps retire against their individual submission fences.
- Scene membership, inspector edits, command undo/redo, and document commits increment the scene revision. The renderer invalidates view history when that revision changes, preventing old TAA samples from surviving an edit.

## Asset loading rules

```text
Request → Queued → Decoding (CPU worker) → ReadyForUpload
        → Uploading (render thread submission + fence) → Ready → scene instance
        ↘ Failed / Cancelled
```

- CPU materials reference decoded images by asset-local index. They contain no device texture IDs. Model instances hold shared immutable CPU assets and GPU residency; importing/reopening the same canonical source reuses those entries.
- Texture and geometry copies for one asset share a direct command context. Upload pages are retired by its fence; texture placement respects 512-byte alignment and each allocation's offset. No per-texture/per-mesh GPU wait occurs on the asynchronous import path.
- A cancelled CPU task never submits. Cancellation after submission retains residency until its fence completes, then discards unpublished geometry. Public snapshots expose drawable GPU residency only in `Ready`.
- Cancellation is cooperative between decode stages and within mesh conversion/rebuild loops. The underlying TinyGLTF file/image read cannot be interrupted mid-call. Shutdown joins the worker and waits for pending uploads before releasing the cache.
- Loader errors, warnings, unsupported primitive/accessor formats, and malformed buffer/index ranges are reported through task snapshots. The existing forward path supports triangle primitives and float vertex attributes; unsupported sparse/quantized accessors fail explicitly.
- Opening a scene or shutting down the editor cancels pending scene imports. Imports that finish normally remain undoable. The ready cache has configurable CPU/GPU soft budgets and evicts unowned entries by last request use. Source-change/reimport detection remains future work.

## Asset residency and budgets

- `ModelAssetManager::Request` returns a copyable `AssetRequest` lease. Consumers keep the lease while waiting for or using its snapshots; the editor's pending imports and scene-loader jobs keep these leases, including already-ready models while other models load. Bare `AssetRequestId` values are diagnostic keys and do not keep cache entries alive. Commit, cancellation and failure release document leases without cancelling another consumer's shared work.
- The default budgets are 512 MiB CPU and 1024 MiB GPU. `SetBudget`, `Trim`, `Update`, uploads and owned texture release run on the render thread. `Update` trims automatically; the Content Browser shows residency, protected entries and evictions and lets the user edit both limits. Zero means no unused cache residency. Active loads, request leases, scene instances, command history and unfinished frame owners can exceed these soft limits. Trimming never waits for rendering or discards an asset that a consumer still owns.
- CPU usage estimates retained asset vector/string storage; it is not process working-set accounting. GPU usage sums the D3D12 committed allocation sizes of model vertex/index buffers and images, including uploads waiting for their fence. Renderer/view targets, environment textures, descriptor heaps, PSOs and upload pages are outside these model-cache budgets. Oversized active imports can therefore exceed the limits; this is an eviction policy, not an allocation admission limit.
- `ModelGPU` owns its image `TextureResidency` objects as well as geometry. The last owner releases each image and recycles its CPU SRV mirror and bindless descriptor slot together. Pending upload records, cancelled submitted uploads and `FrameScheduler` owners provide fence-safe retention. Each new texture receives a monotonically increasing 32-bit ID; IDs never repeat, and an erased ID fails lookup instead of referring to a recycled descriptor's new texture. Live texture wrappers have stable addresses in a map rather than moving during pool growth.
- Unleased failed/cancelled diagnostics are removed after any submitted upload completes. Eviction removes the canonical-path cache link, so a later request decodes/uploads a new entry and receives a new request ID. Service shutdown joins the worker, waits for upload fences and strips cache data even from outstanding request leases. External scene/frame owners still retain their own shared data. Legacy unowned texture APIs and the renderer's HDR source remain device-session owned.

## Scene document transactions

`SceneDocument` owns serialization and validation independently of ImGui panels. Version 3 stores globally unique IDs, the next ID, model references, camera lenses, directional-light parameters, and active camera/light references. Version 1 assigns IDs; nonempty version 1/2 model scenes gain explicit default camera and sun entities, while empty scenes stay empty. Duplicate/invalid IDs across entity types, invalid active references, unsupported versions, empty asset paths, malformed transforms, nonfinite values, zero rotation quaternions, invalid camera clip/FOV ranges, negative radiance, and nonpositive shadow bounds fail before scene replacement. Asset paths inside the project are saved relative to the project root.

Opening a document follows `Queued → Reading → Parsed → LoadingAssets → Ready → Applied`. The worker reads and validates JSON. The render thread requests at most 64 model records per update and waits for every asset's ready residency. It builds all candidate models, cameras and lights before atomically replacing the scene, then updates selection and clears the old document's undo history. Failure, cancellation, and superseded jobs leave the previous scene and history intact. Cancelling a document detaches its shared asset requests; it does not cancel cache work another consumer may still need. The viewport and renderer settings remain usable during loading; scene-editing panels, save, and undo/redo are disabled until it ends.

Save and Save As serialize validated data to an owned sibling temporary file and replace the destination only after the write closes successfully. A failed save preserves the destination. Save still serializes and writes on the main thread; JSON parsing cannot interrupt the underlying stream parser mid-call, and large-document save/commit times remain work for a later stage.

## Reproducible validation

Use PowerShell 7 from the repository root:

```powershell
pwsh -File scripts/Build-Pbr.ps1 -Target All -Configuration Debug -SmokeTest
pwsh -File scripts/Build-Pbr.ps1 -Target All -Configuration Release -SmokeTest
```

The build script discovers MSBuild, fixes the solution root, and normalizes inherited environment variable names. PBR, AtomEditor, Atom core, and ImGui use separate intermediate directories; the dependency project is configured through project-reference properties. The script does not modify dependency source files.

Each runtime check renders 60 frames and exits through normal application cleanup. It renders at 640×360, 641×359, 1024×768, and 8×8; toggles TAA; checks history reset and rounded-up SSAO sizes; and resizes the real main window while checking that view dimensions/history survive. It also creates/resizes an independent view and checks that zero-size requests preserve the active target and legacy scene buffers are absent. The log records frame count, D3D12 error count, device removal, validation availability, view errors, four resize checks, and one window resize. Debug checks require GPU validation and all these gates. Release checks exercise the same lifecycle and resize gates without claiming Debug-layer coverage. These checks do not prove visual correctness or mouse-driven editor workflow behavior.

An additional renderer executes a complete geometry/AO/lighting/post frame into a second view on every smoke frame. It shares `PbrResources`, uses an independent camera and TAA history, resizes to odd dimensions, resets history independently, keeps TAA enabled while the primary view disables it, and is shut down/recreated while the primary renderer continues. Four checks require sharing and a single precompute, rejection of incompatible formats, absence of legacy IBL/global PSO initialization, isolated resize/history, and safe view recreation. Both processes and the build script enforce `multiViewChecks=4 secondViewFrames=60`. This proves actual sequential rendering of two views on the direct queue; cross-queue overlap remains outside these checks. A separate light readback check below compares HDR pixels.

The same smoke run also checks six import cases: a valid `.glb` with canonical-path and shared-residency checks, a missing file, an accessor beyond its buffer view, malformed JSON, cancellation before submission, and cancellation after submission. It checks that GPU data is hidden until ready, that failed/pre-submit-cancelled jobs have no upload fence, and that post-submit cancellation waits for fence completion. The imported valid model is added to the scene and drawn. Fixtures are generated only under ignored `bin-int/smoke-assets`. The build script requires `assetErrors=0 assetChecks=6`. These service checks do not replace UI interaction tests or an import benchmark on large assets.

AtomEditor additionally runs 22 checks against an isolated scene using the same asset manager: transform, model deletion/import, camera creation, light creation and active-light deletion with undo/redo; a failed save preserving an existing file; version 3 roundtrip with IDs/components/shared residency; version 1 and 2 migrations; duplicate model and cross-type IDs; invalid rotation, camera clip range, light color and active references; partial asset failure; cancellation; superseded loads; an empty document; a component-only document; and a transaction loading two new model sources under zero CPU/GPU budgets. The editor checks run with zero budgets, then restore the configured limits. Pending and failed loads must preserve scene revision, selection, and command history. Successful loads must clear history and set selection. Fixtures live under ignored `bin-int/smoke-documents`. Both application exit status and the script enforce completion (`uiErrors=0 uiChecks=22 uiExpected=22`); PBR has no editor dependency and reports zero expected UI checks. These exercise the same document/command services used by panels, not mouse interaction with dialogs or panels.

Both applications run five frame-scheduler checks. A CPU-signalled D3D12 fence gates the direct queue so that three pending frames and retained owners are deterministic, independent of GPU speed. Checks cover API protocol, deduplicated owner retention, distinct slots and the three-frame limit, safe slot reuse, and drain/release. The regular 60 render frames use asynchronous submissions; they also minimize and restore the actual main window and verify that the scene view/history survive both transitions. Both exit status and the script require `frameErrors=0 frameChecks=5 submissions=60 slotReuses=57 drained=1 presentationChecks=2`. Debug GPU validation covers the queued frame path, resizing/minimization, constants, descriptor tables and cleanup. These checks establish bounded queueing and ownership; they are not a frame-rate benchmark, do not exercise detached panels through mouse input, and do not establish cross-queue rendering safety. Any future async compute path must add explicit queue dependencies.

Both applications additionally enforce 12 cache/residency checks (`cacheErrors=0 cacheChecks=12`). Isolated textured triangle fixtures validate CPU estimates/committed GPU accounting, independent CPU and GPU LRU pressure, external CPU ownership, new IDs after eviction, rejection of stale texture IDs, reuse of both SRV descriptor slots, copied request leases, complete release after dropping leases, pending frame retention, release after frame drain, submitted-upload cancellation on an explicitly gated queue, 12 repeated import/eviction cycles with bounded live textures and descriptor reuse, and shutdown with an outstanding request lease. Fixtures live under ignored `bin-int/smoke-cache`. These establish ownership and eviction behavior; they do not measure process memory or large-scene import throughput.


## Scene cameras and directional lighting

- Models, cameras and lights share the scene ID allocator. Camera/light creation, deletion, naming and pose/property edits use the same undo history. Deleting an active component clears its reference; undo restores both the entity and its active state. Document replacement validates membership and active references before swapping all entity collections.
- `RenderView::EditorCamera` retains navigation independently of the actual render camera. Each view can preview the scene's active camera or override it with a particular scene camera ID. Missing sources fall back to editor navigation. Switching mode/source invalidates only that view's temporal history; scene edits invalidate every observing view. Opening a document resets the editor's override to follow the new document's active camera. Camera aspect comes from the viewport, while lens and pose come from the selected scene camera.
- The current forward renderer extracts one active, enabled directional light. Local -Z emits light rays; linear RGB color times intensity becomes direct radiance. No enabled active light produces zero direct radiance while IBL remains. The component's `CastsShadows` and renderer's global shadow setting jointly control shadow rendering/sampling. Shadow bounds are world-space dimensions around `ShadowCenter`; the positive-Z shadow camera starts half the depth span before that center. Point/spot lights and simultaneous multiple direct lights remain future features.

Both applications require `sceneErrors=0 sceneChecks=15`: six entity/transaction invariants, eight rendered-frame checks for camera/lens extraction, per-view overrides, fallback, independent history, light radiance, shadow flags and restoration, plus an HDR pixel comparison. Frames 6/7 copy the primary `SceneColor` texture with identical camera/geometry and enabled/disabled direct light. Only these two smoke probe frames wait for their presentation fences before mapping. The check requires finite RGB values and a nonzero absolute RGB difference, and reports `LIGHT_PROBE`. It demonstrates that scene light state reaches actual shader output; it is not a complete visual regression test.

Readback artifacts are ignored under `bin-int/smoke-light-probe/{PBR,Editor}-{Debug,Release}-{enabled,disabled}.rgba16f`. Each begins with three little-endian uint32 values (width, height, row pitch), followed by padded RGBA half-float rows. `CommandContext::ReadbackTexture` records subresource zero into a caller-owned buffer; the caller retains it through the submission fence and restores the source texture's state. Multisampled textures require a resolve first.
